# rank 가드 — 장애 중 재배치(대체 버킷) 설계

상태: 구현·레인 A 실측(2026-10-21). 기본값은 꺼짐(`DAOS_RANK_GUARD_RELOCATE=1` 로 켬).

## 1. 왜 필요한가

`redundancy: none`(rd_fac 0 + `self_heal:none` + S1 버킷) 풀은 저장 노드 하나가 꺼져
있는 동안 그 노드에 있는 버킷의 키를 **장애 내내 재계산**한다. 재계산한 KV 를 다시
저장해도 키 → 버킷이 해시로 고정이라 같은 죽은 rank 로 가고, breaker 가 그 쓰기를
버린다(레인 A run I·K: 장애 중 반복 TTFT p50 0.66~0.69 s, 재계산 수준).

같은 시나리오에서 Mooncake 는 마스터가 죽은 노드의 세그먼트를 내리고 재계산된 청크를
살아 있는 노드에 다시 놓아, 정지 약 66 s 뒤부터 노드가 꺼진 채로 hit 를 회복했다
(허브 1f09478a §2.10). Mooncake 와 DAOS 를 결합하는 두 경로(§2.11 ①, §2.12 ③)는 이
차이를 메우지 못했다. 이 설계는 DAOS 단독으로, 마스터 없이 같은 효과를 내는 방법이다.

EC 풀(`redundancy: ec`)에는 해당하지 않는다. EC 버킷은 여러 rank 에 걸쳐 있어 DAOS 가
degraded 읽기로 장애 중에도 hit 를 유지한다(run T, W1).

## 2. 지금 구조에서 바꿀 곳

connector(in-process)와 MP 어댑터(`GuardedKV`)는 모두 `GuardedObj` 를 거쳐
`S1BucketStore.fetch / update / punch` 로만 DAOS 에 접근하고, 키 → 버킷은
`S1BucketStore._op` 의 `placement.bucket(dkey)` 한 곳에서 정한다. 재배치는 이
저장소 계층 안에서만 구현한다. connector·`GuardedKV`·serde 는 바꾸지 않는다.

## 3. 제안: 키마다 정해진 대체 버킷 하나

### 3.1 대체 버킷

- 키의 **기본 버킷** `b0 = H(dkey) mod N`(지금과 같음).
- **대체 버킷** `b1` 은 `H(dkey ‖ i) mod N`(i = 1, 2, …)을 차례로 계산해 **기본 버킷과
  다른 rank** 에 있는 첫 버킷이다. 버킷 → rank 는 기동 때 레이아웃으로 이미 안다
  (`BucketPlacement.rank`). `self_heal:none` + S1 이라 장애 중에도 버킷이 옮겨지지 않으므로,
  같은 컨테이너를 여는 모든 프로세스가 언제나 같은 `b1` 을 계산한다. 메타데이터나 색인이
  필요 없다.
- 대체 버킷은 하나만 둔다. 동시에 두 rank 가 꺼져 `b0`, `b1` 이 모두 죽어 있으면 지금처럼
  miss 다(3 노드 rd_fac 0 풀에서는 그 경우 어차피 풀의 2/3 가 없다).

### 3.2 쓰기

| `b0` rank 의 breaker | 쓰기 대상 |
|---|---|
| 닫힘 | `b0`(지금과 같음) |
| 열림·반열림 | `b1`(그 rank 가 닫혀 있으면). 아니면 버림(`Dropped`, 지금과 같음) |

breaker 가 열리기 전의 첫 쓰기 몇 건(기한 초과 2 회)은 지금처럼 `b0` 에서 기한에 걸려
버려진다. 쓰기 결정은 `allow()` 가 아니라 `state()` 로 한다. `allow()` 는 반열림 probe 를
소비하므로, 쓰기가 probe 를 가져가면 장애 중 반열림마다 쓰기 하나가 기한에 걸린다.

### 3.3 읽기

1. `b0` rank 가 허용되면(`allow()`, 반열림 probe 포함) `b0` 을 읽는다. hit 면 끝.
2. `b0` 가 miss 이거나 건너뛰었으면 `b1` rank 가 닫혀 있을 때 `b1` 을 읽는다.

2 번은 장애 중뿐 아니라 **복귀 뒤에도** 필요하다. 장애 동안 `b1` 에 저장된 키는 `b0` 에
없기 때문이다. 내용 해시 키라 `b0`·`b1` 어느 쪽 사본이든 같은 값이다(포기한 쓰기가 늦게
반영돼도 같은 바이트).

`exists`(메타데이터 akey 조회)와 put-if-absent 확인(`_committed`)도 같은 fetch 경로라
그대로 따라온다. 그래서 복귀 뒤 같은 키를 다시 저장하려 해도 `b1` 에서 이미 있음을 보고
쓰지 않는다. 중복 사본이 생기지 않는다.

### 3.4 삭제(punch)와 축출

- `punch` 는 `b0`·`b1` 양쪽에 보낸다(닫힌 rank 만). 키가 어디 있는지 모르므로 양쪽을
  지운다. 축출(1 초 주기)은 punch 가 드물어 비용이 작다.
- 기동 스캔(`list_dkeys`)은 모든 버킷을 훑으므로 `b1` 에 있는 키도 색인에 들어간다.
  같은 키가 두 버킷에 있으면 한 번만 센다.
- 축출이 "열린 rank 의 키는 건너뛴다"는 규칙은 키의 실제 위치가 아니라 `b0` 의 rank 로
  판단하던 것을, `b0`·`b1` 중 **닫힌 쪽에 punch 할 수 있으면** 진행하도록 바꾼다.

### 3.5 끄고 켜기

`DAOS_RANK_GUARD_RELOCATE=1`(MP: `"guard_relocate": true`)로 켠다. 기본은 꺼짐으로 시작해
실측 뒤 기본값을 정한다. EC 버킷(`oclass != S1`)에서는 켜도 무시한다(풀 단위 breaker 라
"다른 rank 의 버킷"이 의미가 없다).

## 4. 비용과 위험

| 항목 | 영향 | 대응 |
|---|---|---|
| 정상 시 miss 비용 | miss 한 번에 `b1` fetch 하나가 더 붙는다(같은 rank 가 아니므로 병렬화 여지 있음). LMCache 는 프리픽스 연속성 때문에 요청당 대개 마지막 한 청크에서만 miss 가 날 것으로 본다(미확인) | 실측으로 확인(정상 구간 TTFT·lookup 시간). 크면 "이 컨테이너에 재배치된 키가 있는가" 표식으로 장애 이력이 없을 때 생략 |
| 장애 중 공간 | rd_fac 0 풀은 장애 중 살아 있는 rank 의 aggregation·GC 가 멈춘다(RANK-GUARD.md §4). 재배치는 그동안 살아 있는 rank 에 쓰기를 더 몰아준다 | 용량 상한 규칙(풀의 1/3 이하 + 장애 시간 × 쓰기 속도)을 그대로 적용. 실측에서 DER_NOSPACE 를 본다 |
| 복귀 뒤 이중 위치 | 장애 중 저장된 키는 `b1` 에 남는다. 다시 `b0` 로 옮기지 않는다 | 불변 키라 정확성 문제 없음. 축출이 정리한다 |
| 반열림 중 읽기 | `b0` probe 가 기한에 걸리면 그 요청은 0.5 s 를 쓴다(지금과 같음) | 변화 없음 |
| 레이아웃이 바뀌는 경우 | `self_heal:none` 이 아닌 풀에서 rebuild 로 버킷이 옮겨지면 프로세스마다 `b1` 계산이 달라질 수 있다 | S1 + `self_heal:none`(kvcache none) 전용으로 제한 |
| 3 노드에서 꺼진 rank 의 부하 | 그 rank 의 몫(약 1/3)이 나머지 두 rank 로 간다 | 공간 규칙에 포함 |

## 5. 시험 계획

1. **단위 시험**(`tests/test_rank_guard.py`, CI unit 잡): 가짜 저장소로
   - `b1` 이 `b0` 와 다른 rank 이고 프로세스가 달라도 같다.
   - `b0` 열림 → 쓰기가 `b1` 로, 읽기가 `b1` 에서 hit.
   - 복귀 뒤(`b0` 닫힘, `b0` miss) 읽기가 `b1` 에서 hit, 같은 키 재저장은 건너뜀.
   - 두 rank 모두 열림 → 지금처럼 miss / `Dropped`.
   - EC 에서는 꺼짐.
2. **레인 A**(run K 와 같은 조건: kvt rd_fac 0, in-process, 16 프롬프트, 240 s 정지):
   - 장애 중 반복 TTFT 가 재계산 수준에서 hit 로 돌아오는 시점. **기준: 정지 뒤 90 s
     안에 hit 회복**(Mooncake 66 s, EC + 가드 80~90 s).
   - 정지 직후 꼬리 지연이 지금 수준(최악 1.3 s)을 넘지 않는다.
   - 정상 구간 반복·처음 보는 프롬프트 TTFT 가 꺼짐과 같다(miss 비용).
   - 요청 실패 0, DER_NOSPACE 여부, 복귀 뒤 hit 유지.
   - MP 모드로 한 번 더(V3b·W1 과 같은 조건).

## 6. 실측 (레인 A, 2026-10-21)

조건: run K 와 같다. 풀 kvt(rd_fac 0, `self_heal:none`), 시험마다 새 컨테이너, 용량 상한 3 GB,
프롬프트 16 개(50 번째마다 처음 보는 프롬프트), 900 s. rank 0(3a, MS·PS 리더 아님)을 240 s 끈다.
같은 이미지(vllm-lmcache-daos 0.30.0-0.5.5-20261021)에 이 브랜치 코드를 올렸다.

| 구간 | in-process, 재배치 끔 | in-process, 재배치 켬 | MP, 재배치 켬 |
|---|---|---|---|
| 정상 반복 p50 / 처음 보는 프롬프트 p50 | 0.157 / 0.766 s | 0.156 / 0.762 s | 0.181 / 0.730 s |
| 정지 직후 90 s | 0.675 s(재계산) | **0.180 s** | **0.191 s** |
| 정지 90 s ~ 전원 켬 | 0.729 s | **0.182 s** | **0.196 s** |
| 전원 켬 ~ Joined | 0.726 s | **0.182 s** | **0.203 s** |
| Joined 뒤 | 0.160 s | 0.159 s | 0.185 s |
| 최악 | 1.29 s | 1.28 s | 1.22 s |
| 요청 / 실패 | 4,302 / 0 | 5,470 / 0 | 4,517 / 0 |

- **장애 중 hit 가 정지 뒤 첫 15 s 구간부터 돌아왔다**(15 s 단위 p50 이 내내 0.18~0.20 s). 기준(90 s
  안)을 넘었고, Mooncake 의 66 s(허브 1f09478a §2.10)보다 빠르다. breaker 가 열리자마자 재계산된
  KV 가 대체 버킷으로 저장되고, 프롬프트 16 개가 한 바퀴 도는 사이에 다시 읽히기 때문이다.
- **정상 시 비용은 보이지 않았다.** 재배치를 켜도 정상 구간의 반복·처음 보는 프롬프트 TTFT 가
  같다(miss 당 대체 버킷 fetch 하나).
- **공간:** in-process 재배치 켬에서 rank 가 다시 합류한 직후 10 s 사이에 살아 있는 rank 하나의
  target 에서 DER_NOSPACE 9 건(쓰기 버림, 요청 실패 아님). 장애 동안 그 rank 에 쌓인 재배치 쓰기를
  aggregation 이 복귀 직후에야 몰아서 회수한 시점과 겹친다. MP(L2 축출) 에서는 0 건. §4 의 용량
  규칙(풀의 1/3 이하 + 장애 시간 × 쓰기 속도)을 그대로 지킨다.
- MP 재배치 없음의 참고값: run P(10-16) 장애 중 반복 p50 0.562 s.

원자료: `daos-reboot-repro/2026-10-21-reloc/`(`run.sh`, `compare.py`, `vllm-rl0.yaml`, `vllm-rl1.yaml`,
`vllm-rlmp.yaml`, `rl0`, `rl1`, `rlmp`).

## 7. 고려했다 버린 방법

| 방법 | 버린 이유 |
|---|---|
| rank 가 꺼지면 모든 키를 다시 해시(버킷 수를 살아 있는 rank 로 줄임) | 복귀 순간 모든 키의 위치가 다시 바뀌어 장애 전 데이터가 전부 miss. 프로세스마다 장애 인식 시점이 달라 위치가 갈린다 |
| 키 → 위치 색인(메타 서버 또는 컨테이너 안 색인 객체) | 마스터 의존이 생긴다. 색인 객체가 죽은 rank 에 있으면 같은 문제. 이 프로파일의 장점(데이터 경로에 메타 왕복 없음)을 잃는다 |
| 쓰기를 항상 두 버킷에(rd_fac 0 위의 응용 수준 복제) | 쓰기·공간 2 배. 그 값이면 EC 2+1(1.5 배)이 낫다 |
| 대체 버킷 여럿 | 3 노드에서는 한 rank 장애만 의미가 있고, 읽기 miss 비용이 대체 개수만큼 는다 |
