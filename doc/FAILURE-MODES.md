# 장애 모드 — DAOS 가 잘못될 때 LMCache 가 실제로 보는 것

지금까지 이 리포의 모든 숫자는 **건강한 풀** 에서 나왔다. 그것은 이 백엔드를
출시할 수 있는지를 결정하는 경우에 대해 아무것도 말해 주지 않는다. 서빙
프로세스는 스토리지가 이상해졌다고 해서 멈출 수 없으므로, 실제로 중요한 질문은
하나뿐이다. **장애가 깨끗한 오류로 도착하는가, 멈춤으로 도착하는가, 틀린 바이트로
도착하는가.**

판정 기준은 이 순서다.

| | | |
|---|---|---|
| **WRONG** | `get()` 이 `put()` 이 쓰지 않은 데이터를 돌려줌 | 어떤 빈도든 허용 불가. vLLM 이 그대로 서빙한다. v1 객체 형식에는 페이로드 체크섬이 없어 아래 하네스 말고는 아무도 알아채지 못한다 |
| **HANG** | 예산 안에 돌아오지 않음 | 거의 그만큼 나쁘다. 요청 스레드가 사라지고, 블로킹 DAOS 호출은 `run_in_executor` 스레드 안에 있으므로 asyncio 취소로는 풀려나지 않는다 |
| **raise** | 깨끗한 실패 | 괜찮다. LMCache 가 miss 로 취급하는 한 |

`miss` 는 **완전히 쓰이지 못한 객체에 대한 정답**이다. 절단 형태 자체는
`tests/test_torn_object.py` 가 직접 다루고, 여기서는 인위적으로 자른 파일이 아니라
실제 크래시의 결과로 확인한다.

- 하네스: `tests/failure_modes.py` (시나리오 1개 = 프로세스 1개)
- 구동기: `tests/failure_modes.sh` (결함 주입 + 순서 + 복구)
- 단위 시험: `tests/test_wedge.py` (아래 고착 감지)

## 측정 환경

cxl2 (`memfs.rnd.gluesys.com`), DAOS 2.8.0, 엔진 1개 / 타깃 4개, tcp
(`enp1s0f0np0`), SCM = 램디스크 8 GB, 데이터 = NVMe `0000:c1:00.0` (1.6 TB).

**순서는 취향이 아니라 강제된 것이다.** SCM 이 램디스크라 `daos_server` 를 내리면
풀이 사라진다. 풀이 살아남는 결함을 먼저 전부 돌리고, 서버 정지 단계는 마지막에
와야 한다. 이 제약이 주장할 수 있는 범위도 정한다 — 맨 아래 "답하지 못한 것" 참고.

**틀린 바이트는 어느 시나리오에서도 나오지 않았다.** 이건 그냥 통과가 아니라, 이

풀 고갈은 이 중 유일하게 **스스로 찾아오는** 장애다. 아무것도 고장나지 않았고
아무도 잘못하지 않았으며, 캐시가 제 일을 하다가 자리가 없어졌을 뿐이다. LMCache 는
풀 크기를 모르므로 영원히 `put()` 을 계속 부른다. 그래서 중요한 것은 쓰기가
실패한다는 사실이 아니라 — 실패해야 한다 — 그 실패가 **값싸고, 반복 가능하고,
읽기 경로를 같이 끌고 내려가지 않는다**는 점이다. 쓰기를 그만 받는 순간 히트도
못 주는 백엔드는 가득 찬 캐시를 장애로 바꾼다. 측정 결과 그렇지 않다.

### 확인된 것 하나: `daos_agent` 는 I/O 경로에 없다

핸들이 한 번 열리고 나면 에이전트를 죽여도 읽기와 쓰기가 그대로 동작했다.
클라이언트는 시작할 때 유닉스 소켓으로 에이전트에게 시스템 정보와 자격을 받고,
그 뒤에는 패브릭으로 엔진과 직접 말하기 때문이다. 추측이 아니라 측정이다.

부수적으로 얻은 운영 함정 하나. **SIGKILL 된 에이전트는 그냥은 다시 뜨지
않는다.**

```
ERROR: daos_agent: unable to start dRPC server: unable to listen on unix socket
/var/run/daos_agent/daos_agent.sock: bind: no such file or directory
```

`/var/run/daos_agent` 디렉터리가 없어서다. systemd 유닛이
`RuntimeDirectory=daos_agent` 로 선언하므로 그 디렉터리는 systemd 소유다.
`systemctl start daos_agent` 로 올리거나, 손으로 띄울 거면 `mkdir -p` 를 먼저
해야 한다.

## 진짜 발견 — 죽은 엔진을 향한 DAOS 호출은 돌아오지 않는다

`batched_put` 도중 `daos_server` 를 SIGKILL 했을 때:

```
Thread 3400968 (idle): "MainThread"
    _wait_for_tstate_lock (threading.py:1169)
    join (threading.py:1149)
    shutdown (concurrent/futures/thread.py:239)
    close (lmcache_daos/connector.py:658)      <- 여기서 영영 멈춤
Thread 3401076 (active): "daos-io_0"
    write_obj_from (lmcache_daos/dfs_binding.py:404)
    _put_sync (lmcache_daos/connector.py:575)
```

| | |
|---|---|
| 고착된 스레드 | **16 / 16** — 풀 전체 (`DAOS_WORKERS` 기본값) |
| 경과 | **1016 초** 시점에 여전히 그 상태 |
| CPU | **1312 %** — 약 13 코어. 잠든 게 아니라 **돌고 있다** |
| `CRT_TIMEOUT=10` | **효과 없음.** 786 초에 13 스레드, 1411 % |

세 가지가 동시에 참이다.

1. **풀이 프로세스 수명 동안 끝난다.** C 호출 안에 들어간 스레드는 파이썬에서
   취소할 수 없다. `asyncio.wait_for()` 는 기다림을 포기할 뿐 스레드는 그대로
   사라진다. 이후 제출되는 모든 작업은 영원히 그 뒤에 줄 선다.
2. **`close()` 가 돌아오지 않았다.** `self._pool.shutdown(wait=True)` 가 그
   스레드들을 join 한다. 바로 두 줄 아래 주석이 ping 풀에 대해 이 위험을 정확히
   설명하며 `wait=False` 를 고른 상태였는데, 데이터 풀은 `wait=True` 로 남아
   있었다.
3. **서빙 프로세스에서 13 코어를 태운다.** 백엔드 장애 위에 얹히는 순수한
   처리량 손실이다.

### 네 경로 모두 같은 구조다

읽어서 확인했다. 추론이 아니다.

| 경로 | 블로킹 호출 | 실행 위치 |
|---|---|---|
| in-process 커넥터 | `dfs_sys_*` | `ThreadPoolExecutor` |
| MP L2 어댑터 | `dfs_sys_*` (`DfsSys` 직접) | `ThreadPoolExecutor` |
| NIXL 플러그인 | `daos_obj_fetch/update` | `nixlDaosThreadPool` |
| GDS | 같은 DFS 경로 | 같음 |

MP 모드가 별도 프로세스라서 구조적으로 면제될 거라고 생각했는데, **아니다.**
`lmcache_daos/mp/l2_adapter.py` 는 `DfsSys` 를 직접 쓰는 스레드풀이다. 지금 고친
것은 in-process 커넥터뿐이다.

## 바꾼 것

### 1. `close()` 가 고착된 스레드를 join 하지 않는다

`shutdown(wait=False, cancel_futures=True)`. 아직 시작하지 않은 작업만 취소되며,
이미 libdaos 안에 들어간 스레드는 우리가 회수할 수 있는 것이 아니다.
`cancel_futures` 는 3.9+ 라 `pyproject.toml` 의 `>=3.8` 하한에 맞춰 버전으로
분기한다.

**이걸로 프로세스가 종료 가능해지지는 않는다.** `concurrent.futures` 가
`_python_exit` 를 등록해 인터프리터 종료 시 모든 워커를 join 하기 때문이다.
직접 확인했다 — 30 초 sleep 하나만 물린 프로세스는 `shutdown(wait=False)` 가
돌아온 뒤에도 **30 초를 다 살았다**. (그 스레드는 `daemon=True` 였다. 데몬 여부는
상관없다.) 여기서 벗어나려면 호출 자체가 유한해야 하고, 그건 파이썬 문제가 아니라
DAOS 문제다.

### 2. 고착을 감지하면 줄 서지 않고 즉시 실패한다

영원히 줄 서는 것은 실패하는 것보다 **엄격히 나쁘다.** LMCache 는 raise 된
`get`/`put` 을 miss 로 보고 모델로 서빙하지만, 돌아오지 않는 제출은 요청을 통째로
가져간다.

```python
STALL_SECS = float(os.environ.get("DAOS_STALL_SECS", "60"))

class DaosPoolWedged(DaosError):   # rc = EBUSY
```

판정은 **"모든 워커가 바쁘고 + `STALL_SECS` 동안 완료가 하나도 없음"** 이다.
포화만으로는 증거가 못 된다 — 큰 저장은 16 워커를 몇 분씩 정당하게 채운다. 부하
중에는 완료가 계속 도착하고, 고착에는 완료가 **정확히 0** 이다. 이 구분이
없으면 감지기는 자기가 지키려던 부하에서 백엔드를 내려 버린다.
`tests/test_wedge.py` 가 이 오탐 사례를 직접 시험한다.

`ping()` 도 같이 본다. 탐침은 자기 스레드에서 돌기 때문에, 데이터 워커 전부가
몇 분째 막힌 풀에서도 명랑하게 0 을 돌려줄 수 있다. 헬스체크가 LMCache 에게 계속
일을 보낼지 결정하는 주체이므로, 그 보고만은 틀리면 안 된다.

### 효과 — 같은 행렬을 다시 돌린 결과

고치기 전후로 바뀐 것은 이렇다.

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| SIGKILL 후 읽기 48건 | 건당 멈춤, 예산만 태움 | **raise=48, hang=0** — 즉시 실패 |
| `close()` | 돌아오지 않음 | 즉시 반환 |
| 구동기 전체 | 4/5 단계에서 멈춰 **복구까지 못 감**, 손으로 죽여야 했음 | **5/5 + 복구까지 완주** |

`batched_put` 자체는 여전히 예산까지 멈춘다(30 s). 그건 유한하지 않은 DAOS 호출
이고 파이썬에서 손댈 수 없다. 바뀐 것은 **그 뒤에 오는 모든 것**이다.

**비용**: 연산당 0.59 µs (잠금 2회 + 래퍼 호출 1회). 측정된 NIXL 요청당
오버헤드 76 µs 의 **0.78 %**, DFS 객체당 630 µs 에 비하면 무시할 수준이다.
추정이 아니라 `timeit` 20만 회다.

## 저수준 객체 API 는 다른가 — 측정

DFS 를 dkey/akey 로 바꾸자는 이유는 성능이다. 객체당 고정비가 **0.63 ms 대
0.0137 ms** 로 46배 차이다 (`doc/LAYERWISE-MEASUREMENT.md`). 그런데 같은 결함
아래서 저수준이 어떻게 행동하는지는 아무도 재지 않았고, "다른 API 니까"는 근거가
아니다. `tests/obj_failure.c` 가 그걸 잰다. 위와 똑같은 결함 — 쓰기 도중
`daos_server` SIGKILL, 스레드 16개, 8 MiB 업데이트.

| arm | 결과 | 잃은 스레드 |
|---|---|---|
| `sync` — `daos_obj_update(..., NULL)` | **16/16 이 150 초 뒤에도 호출 안** | **16** |
| `async` — 이벤트 큐 + `daos_eq_poll` 타임아웃 | 16/16 이 **5.01 초**에 스스로 포기, 총 5.4 초 | **0** |
| `async-abort` — 위 + `daos_event_abort`/`fini` | 같음. **abort 0.00 s, fini 0.00 s** | **0** |

**차이는 "저수준이냐 DFS 냐"가 아니라 "블로킹이냐 이벤트 큐냐"다.** 저수준의
블로킹 형태는 DFS 와 정확히 똑같이 고착된다 — 16/16, 구분이 안 된다. DFS 가
아예 못 하는 것은 이벤트 큐 쪽이다.

그리고 **지금 NIXL 플러그인은 블로킹 형태를 쓴다.** `nixl/plugin/daos_backend.cpp`
가 `daos_obj_update(..., nullptr)` 로 부른다. 즉 저수준으로 옮기는 것만으로는
장애 거동이 하나도 나아지지 않는다. 이벤트 큐까지 가야 한다.

### 이게 왜 위의 미해결 질문과 독립인가

앞에서 무한 고착이 단일 랭크 인공물일 가능성을 열어 뒀다 — SWIM 이 죽은 랭크를
축출할 정족수가 없어서. **`async` 결과는 그 질문에 영향을 받지 않는다.** 5.01 초
경계는 DAOS 가 포기해서 생긴 게 아니라 **호출자가 정한 것**이기 때문이다. DAOS 가
영원히 재시도하든 60 초에 포기하든 결과는 같다. 지금 커넥터가 고착 감지기로
흉내 내야 했던 성질을, 이벤트 큐는 그냥 갖고 있다.

### 값은 치른다

`daos_eq_poll` 이 타임아웃으로 돌아왔을 때 **RPC 는 여전히 진행 중이다.**
스레드는 회수되지만 연산은 취소되지 않는다. 이벤트를 그냥 버리면 DAOS 가 곧 죽을
스택 프레임을 가리키게 된다 — 처음 측정한 `async` arm 이 정확히 그랬고, 그래서
`async-abort` arm 을 따로 만들었다. 결과는 **abort 도 fini 도 0.00 초**라 정리
비용은 없다. 탈출구가 막힘을 다른 데로 옮기지 않는다.

### GPU 진입점도 이벤트를 받는다 (주석이 틀렸다)

플러그인 안에 "GPU 진입점은 동기 전용 — 이벤트 큐 없음"이라는 주석이 있었고, 그걸
근거로 "그래서 스레드에 올린다"고 적혀 있었다. **틀렸다.**

`theodore/b_cufile` 의 `src/client/api/object.c` 에서 두 함수는 `ev` 를 **똑같이**
다룬다. 차이는 GPU_DIRECT 플래그와 `mem_attrs` 뿐이다.

```c
:197 daos_obj_update     → dc_obj_update_task_create(oh, th, flags,              ..., ev, NULL, &task)
:213 daos_obj_update_gpu → dc_obj_update_task_create(oh, th, flags|GPU_DIRECT,   ..., ev, NULL, &task)
                           args->mem_attrs = mem_attrs
```

선언도 마찬가지다 — `daos_obj_update_gpu(..., daos_mem_attr_t *mem_attrs,
daos_event_t *ev)`, `daos_obj_fetch_gpu(..., daos_mem_attr_t *mem_attrs,
daos_iom_t *ioms, daos_event_t *ev)`. 헤더 주석도 비-GPU 판을 그대로 가리키며
`ev` 가 NULL 이면 블로킹이라고 적어 뒀다.

따라서 플러그인의 `nullptr` 은 **제약이 아니라 선택**이고, 지금은 틀린 선택이다.
`VRAM_SEG` 경로도 위 `async` arm 의 5초 탈출구를 가질 수 있다.

**확인 범위**: 초안 브랜치의 **소스**를 봤다. GPU 호스트에 설치된 바이너리가 이
브랜치에서 빌드된 것이라면 같지만, 그건 확인하지 않았다. GPU 경로의 장애 거동을
실제로 **측정한 것도 아니다** — API 가 이벤트를 받는다는 사실만 확정했다. 측정은
GPU 호스트가 있어야 한다.

## 고친 것 셋: NIXL 플러그인에 시한을 줬다

`NIXL_DAOS_EQ_TIMEOUT` 에 초를 넣으면 블로킹 호출 대신 이벤트 큐에 제출하고 그
시한으로 폴링한다. 안 넣거나 `0` 이면 지금까지와 같은 블로킹이다.

플러그인을 통해 `daos_server` 를 읽기 도중 죽였을 때:

| | 결과 |
|---|---|
| 블로킹 | **120 초** 뒤에도 살아있음, 스레드 65개 고착 |
| `NIXL_DAOS_EQ_TIMEOUT=8` | **8 초** 만에 종료, 스레드 전부 회수 |

### 스레드당 EQ 는 함정이었다

처음엔 `thread_local` 로 스레드마다 EQ 를 만들었다. **블로킹보다 35% 느렸다**
(2.08 대 3.12 GB/s). 스레드풀이 일부러 크게 잡혀 있기 때문이다 — 64 스레드가
많아야 `inflight` 개의 요청을 처리한다. **놀고 있는 스레드는 공짜지만 놀고 있는
EQ 는 network context 를 쥔다.** 요청 16개를 돌리려고 context 64개를 산 셈이다.

요청 단위로 **빌려 쓰게** 고치니 사라졌다. EQ 는 요청 하나 동안만 붙잡히므로 집합이
실제 최대 동시성까지만 자라고 더는 안 자란다. 스레드 수와 무관해진다.

| | 64 스레드 | 16 스레드 |
|---|---|---|
| 블로킹 | 3.16 GB/s | 3.12 GB/s |
| EQ, 스레드당 1개 | 2.08 | 3.24 |
| EQ, 빌려 쓰기 | **3.24** | **3.26** |

덤으로 스레드당 방식이 공짜로 갖던 성질도 유지된다 — 두 스레드가 같은 EQ 를 동시에
쥐지 않으므로 폴링이 남의 완료를 가로챌 수 없다.

### 400G verbs 에서 재봤다 — 비용이 없다

위 스윕은 cxl2(단일 노드 TCP, 3 GB/s)에서 한 것이라 **블로킹이 이겼던 구간에
닿지 못했다.** client-5 ↔ cell1/cell2 의 `ofi+verbs;ofi_rxm`, 2랭크 × 8타깃에서
같은 하네스로 4회씩 다시 쟀다.

| | 회차 | 평균 |
|---|---|---|
| 블로킹 | 31.29 · 31.00 · 30.70 · 31.15 | **31.04 GB/s** |
| 이벤트 큐 | 30.44 · 31.27 · 30.23 · 30.61 | **30.64 GB/s** |

**범위가 겹친다.** 이벤트 큐가 블로킹을 이긴 회차도 있다. 접지 않은 경우(요청
4800개)도 7.55 대 7.50 으로 같다.

옛 기각 근거("EQ 는 어떻게 배치해도 7–12 GB/s")는 **이 형태로 옮겨오지 않는다.**
그래서 **기본값을 켰다.** 비용이 없는 시한이 영구히 잃은 스레드 16개를 유한한
오류로 바꾸는 것은 교환이 아니다.

기본 60초는 지연 목표가 아니라 죽은 엔진에 대한 안전장치다 — verbs 에서 요청 하나가
1.34 ms 였으니 네 자릿수 여유가 있다.

### 측정하다 걸린 함정: 컨테이너 `rd_fac`

처음엔 측정이 아예 안 됐다. `test_xfer` 가 20분씩 99.8 % CPU 로 돌며
`DER_HG(-1020)` 를 rank 0 tag 7 에 15초 간격으로 반복했다. 플러그인에 워밍업
코드가 없는 것을 보고 알려진 rdma_cm 스톨을 의심했는데, **아니었다.**

풀 기본값으로 만든 컨테이너는 `rd_fac=1` 이었고, 동작하는 컨테이너들은 전부
`rd_fac=0` 이었다. `--properties=rd_fac:0` 으로 만드니 11/11 통과했다.
9/12 자 원본 플러그인도 똑같이 멈췄으므로 **플러그인 결함이 아니다.**

같은 풀에서 DFS(`daos fs check`)는 1초 만에 정상 완료한다. 저수준 객체 경로만
걸린다.

### 옛 기본값 결정 (기록)

`doc/DESIGN-AND-VALIDATION.md` 의 옛 기각 근거("EQ 는 어떻게 배치해도 7–12 GB/s")는
**DFS 비동기 경로를 파이썬으로 28 MiB 읽기** 한 스윕에서 나왔다. 접힌 객체 API
요청에서는 재현되지 않는다. 그렇다고 반박된 것도 아니다 — cxl2 는 단일 노드 TCP 라
3 GB/s 에서 패브릭이 병목이고, **블로킹이 이겼던 400G verbs 34 GB/s 구간에 닿지
못한다.** EQ 당 network context 비용이 드러나는 곳은 거기다. 기본값을 바꾸려면 그
호스트가 필요하다.

## 답하지 못한 것

이건 한계이지 TODO 가 아니다. 지금 장비에서 답할 수 없다.

| 질문 | 왜 못 하나 | 필요한 것 |
|---|---|---|
| 크래시 때 날아가던 객체가 디스크에 **절단**(→ miss, 정답)으로 남나, **완전한데 틀리게** 남나 | SCM 이 램디스크라 복구 = 재포맷. 증거가 같이 사라진다 | MD-on-SSD |
| 무한 재시도가 **단일 랭크 특성**인가 | 랭크가 하나뿐이라 SWIM 이 죽은 랭크를 축출할 정족수가 없다. 다중 랭크 클러스터라면 축출 후 오류가 떴을 수 있다 (단 위 `async` 결과는 이 질문과 무관하다) | cell1/cell2 |
| 400G verbs 에서 EQ 경로의 처리량 | cxl2 는 3 GB/s 에서 패브릭 병목이라 블로킹과 구분이 안 된다 | cell1/client-5 |
| GPU 경로의 **실측** 장애 거동 | 소스상 이벤트를 받는 건 확정. 실제로 5초에 빠져나오는지는 안 재봤다 | GPU 호스트 |
| 랭크 손실 · 네트워크 분단 | 노드가 하나다 | cell1/cell2 |


첫 두 줄이 중요하다. 무한 고착이 단일 노드 인공물일 **가능성이 있고**, 그렇다면
심각도는 낮아진다. 다만 **클라이언트 쪽 구조는 클러스터 크기와 무관하게 같다** —
커넥터는 데이터 경로에 자기 시한이 없다. ping 경로는 `PING_TIMEOUT_SECS` 를
받았지만 읽기·쓰기는 받지 못했다. 이번에 넣은 것은 시한이 아니라 **고착을
알아보고 더 이상 줄 세우지 않는 것**이다.
