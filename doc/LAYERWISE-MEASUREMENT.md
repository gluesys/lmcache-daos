# LMCache layerwise 모드 실측 (2026-09-11, client-5)

## 요약

`use_layerwise: True` 는 우리 `DaosConnector` 에 **코드 수정 없이 붙는다.** 적중률도 100% 다.
그런데 같은 `chunk_size` 에서 적중 TTFT 가 **11.5배 느리다.** 바이트는 동일하고 객체 수만
레이어 수(40)배로 늘어나기 때문이다.

원인은 대역폭이 아니라 **객체당 약 0.63 ms 의 고정 비용**이다. 객체 크기를 세 가지로 바꿔
직선을 맞춰 분리했고, 워커 수를 바꿔도 변하지 않음을 확인했다.

한 가지는 layerwise 가 이긴다. **콜드 미스 TTFT 가 절반이다.** 저장이 레이어 계산과 겹친다.

## 환경

client-5, Qwen3-14B(40 레이어, KV 헤드 8, head_dim 128, bf16), `--max-model-len 32768`,
`--enforce-eager --no-enable-prefix-caching`, DAOS 2.9.100 stockfull, pool `attr1`,
컨테이너 `kvlmc5`(S16, chunk 4 MiB, rd_fac:0), 전송 `ofi+verbs;ofi_rxm`,
에이전트 domain `mlx5_0`, `local_cpu: false`, IO 스레드풀 16(명시하지 않은 경우).
하네스는 `bench/sweep2.py`(고정 토큰열, `prompt_token_ids` 전송).

`chunk_size: 256` 에서 레이어 하나의 청크는 정확히 1 MiB 다
(256 토큰 × 8 헤드 × 128 dim × 2(K,V) × 2 B). 전체 레이어를 합치면 40 MiB.

## 적중 TTFT (ms)

| ctx | base/256 | base/1024 | lw/256 | lw/1024 | lw/4096 |
|---|---|---|---|---|---|
| 8192 | 166 | **145** | 982 | 340 | 270 |
| 16384 | 176 | **159** | 1843 | 595 | 330 |
| 30720 | 290 | **269** | 3343 | 1075 | 464 |

`lw/256` 은 세 컨텍스트 모두 `sweep2.py` 의 `hit < miss/2` 게이트를 통과하지 못해
INVALID 로 표시됐다. 캐시가 안 맞은 것이 아니라(로그는 `Retrieved 30720 out of 30720`),
적중이 재계산 대비 2배도 못 줄인 것이다.

## 미스 TTFT (ms) — 여기서는 layerwise 가 이긴다

| ctx | base/256 | base/1024 | lw/256 | lw/1024 | lw/4096 |
|---|---|---|---|---|---|
| 8192 | 883 | 1391 | 1275 | 785 | **620** |
| 16384 | 2379 | 2854 | 2344 | 1419 | **1338** |
| 30720 | 5579 | 5756 | 4462 | 2976 | **2837** |

30720 에서 `base/1024` 5756 ms → `lw/4096` 2837 ms 로 **2.03배** 빠르다.
저장이 레이어별로 일어나 전방 계산과 겹치기 때문이다. 비layerwise 는 forward 가 끝난 뒤
한꺼번에 저장하므로 첫 토큰이 그만큼 밀린다.

## 고정 비용 분리

30720 기준, 유효 객체당 시간 = 벽시계 시간 / 객체 수 (워커 16 포함된 값).

| arm | 객체 수 | 객체 크기 | 벽시계 | 객체당 |
|---|---|---|---|---|
| lw/256 | 4800 | 1 MiB | 3343 ms | 0.696 ms |
| lw/1024 | 1200 | 4 MiB | 1075 ms | 0.896 ms |
| lw/4096 | 280 | 16 MiB | 464 ms | 1.657 ms |

세 점이 직선에 잘 맞는다.

```
t_eff(size) ≈ 0.63 ms + 0.067 ms/MiB
```

1 MiB 와 4 MiB 두 점으로 맞춘 뒤 16 MiB 를 예측하면 1.70 ms 가 나오고 실측은 1.657 ms 다.

기울기를 대역폭으로 환산하면 15.7 GB/s 다. **데이터를 옮기는 능력은 정상이다.**
문제는 절편이다. 1 MiB 객체에서는 시간의 **90%가 고정 비용**이다.

| 객체 크기 | 고정 | 이동 | 고정 비중 |
|---|---|---|---|
| 1 MiB | 0.63 ms | 0.07 ms | 90% |
| 4 MiB | 0.63 ms | 0.27 ms | 70% |
| 16 MiB | 0.63 ms | 1.07 ms | 37% |

## 워커를 늘리면 오히려 나빠진다

`lw/256` 을 IO 스레드풀 16 과 128 로 각각 측정했다.

| ctx | 16 워커 | 128 워커 |
|---|---|---|
| 8192 | 982 ms | 1084 ms |
| 16384 | 1843 ms | 2009 ms |
| 30720 | 3343 ms | 3660 ms |

8배를 늘렸는데 9~10% 느려졌다. 고정 비용이 **동시성으로 감춰지지 않는 직렬 구간**이라는 뜻이다.
`connector.py` 의 P4 주석에 적힌 관찰(per-EQ `eqx_lock` 이 submit+completion 을 직렬화해
큐 배치와 무관하게 7~12 GB/s 에서 막힘)과 같은 방향이다.

이 실험을 위해 하드코딩된 `self._workers = 16` 을 `DAOS_WORKERS` 환경변수로 열었다.
기본값은 그대로 16 이라 기존 동작은 변하지 않는다.

## 차단(blocking) 경로가 비차단 경로보다 빠르다

`base/*` 는 `batched_get`(차단), `lw/*` 는 `batched_get_non_blocking` 을 탄다.
같은 모델로 base 를 예측하면 실측이 일관되게 21~27% 빠르다.

| arm | 객체 크기 | 예측 | 실측 | |
|---|---|---|---|---|
| base/256 | 40 MiB | 3.31 ms | 2.42 ms | 27% 빠름 |
| base/1024 | 160 MiB | 11.4 ms | 8.97 ms | 21% 빠름 |

비차단 경로의 asyncio 래핑 비용으로 보인다. 이는 `support_batched_get_non_blocking()` 을
False 로 둔 기존 판단(2026-08-25)을 다시 뒷받침한다.

## 상류 버그: layerwise 해제 경로의 이중 free

`lw/*` 실행 중 메모리 오브젝트마다 다음 경고가 쏟아진다.

```
Ref count of MemoryObj <addr> is negative: -1.
Double free occurred somewhere. Setting ref count back to 0 as a hack but please ...
```

LMCache 0.5.2 `retrieve_layer` 의 정리 구간이 `ref_count_down()` 을 중복 호출한다.
`dev` 에도 같은 구조가 남아 있다(루프에서 `ref_count_down()` 을 돌린 뒤 다시 `unpin()`
루프를 돈다). 상류 보고 대상이다. 기능은 동작하므로 성능 수치에는 영향이 없어 보이나
검증하지 않았다.

## 판정

- **읽기 위주 KV 재사용에는 layerwise 를 켜지 말 것.** 어떤 청크 크기에서도 기본 모드를
  이기지 못한다. 최선끼리 비교해도 464 ms 대 269 ms 로 1.7배 뒤진다.
- 지금 설계(모든 레이어를 한 객체에)는 DAOS 에서 **옳은 선택**이다. 고정 비용을 분산시킨다.
  layerwise 는 정확히 그 이점을 되돌린다.
- **콜드 미스 지연이 중요한 워크로드라면 재고 가치가 있다.** 2배는 작지 않다.
  다만 그 경우에도 `chunk_size` 를 1024 이상으로 올려야 한다.

## 하드웨어 요구사항으로의 환산

`lw/256` 이 `base/1024`(269 ms)를 따라잡으려면 4800 객체를 269 ms 에 처리해야 하므로
객체당 0.056 ms 가 필요하다. 현재 0.696 ms 이니 **약 12배** 줄여야 한다.

즉 "레이어 스트리밍이 이기려면 객체 조회 고정 비용이 12배 싸져야 한다" 가 이 측정의
정량적 결론이다. DPU 쪽 KV 인덱스 아이템의 근거 수치로 쓸 수 있다.

## 재현

```bash
# client-5 (cell1 경유)
CHUNK=1024 DAOS_WORKERS=16 bash /root/launch.sh layerwise
podman exec -e ARM=lw_c1024 -e CTXS=8192,16384,30720 vllm-daos \
    python3 /cfg/bench/sweep2.py
```

`launch.sh` 는 `deploy/launchers/run_vllm_perf_c5.sh` 에서 파생했고 `MODE`(base|layerwise),
`CHUNK`, `DAOS_WORKERS` 를 받는다.

# 후속: dkey/akey 레이아웃은 이 고정 비용을 걷어낸다 (2026-09-11)

위 결론은 "layerwise 는 DAOS 에 맞지 않는다" 처럼 읽히지만, 정확히는
**layerwise 는 DFS 에 맞지 않는다** 였다. 같은 워크로드를 raw object API 로 다시
재니 고정 비용이 무너진다.

`tests/obj_latency.c` 가 그 측정이다. 레이아웃은
`doc/lmcache-mp-l2-assessment.md` 가 "접으려면 필요하다" 고 적었던 바로 그것이다 —
객체 하나(클래스 S16, dkey 가 16 타깃에 흩어진다), **dkey = 청크, akey = 레이어**.

## 결과 (120 청크 × 40 레이어 × 1 MiB = 4.69 GiB, 16 스레드, S16, rd_fac:0)

| 팔 | 의미 | RPC | 벽시계 | 객체당 | GB/s |
|---|---|---|---|---|---|
| `sep` | 레이어마다 fetch 1회 — layerwise 와 같은 모양 | 4800 | **245 ms** | **0.051 ms** | 20.5 |
| `batch` | 청크마다 fetch 1회, akey 40개를 iod 배열로 | 120 | **204 ms** | 0.042 ms | 24.7 |
| `one` | 청크마다 단일 akey 40 MiB — 지금 저장 형태 | 120 | 571 ms | 0.119 ms | 8.8 |

비교 대상: DFS 경로의 같은 모양(4800 × 1 MiB)은 TTFT 3343 ms 였다.

## 고정항

`sep` 을 세 크기로 재서 직선을 맞췄다.

| 레이어 크기 | 객체당 |
|---|---|
| 256 KiB | 0.025 ms |
| 1 MiB | 0.050 ms |
| 4 MiB | 0.168 ms |

```
object API : t ≈ 0.0137 ms + 0.0385 ms/MiB     (26 GB/s 한계)
DFS        : t ≈ 0.63   ms + 0.067  ms/MiB     (15.7 GB/s 한계)
```

고정항이 **0.63 → 0.0137 ms** 다. 기울기도 1.7배 낫다.

## 요구사항을 넘겼다

위에서 "layerwise 가 최선 베이스라인(269 ms)을 따라잡으려면 객체당 0.056 ms 가
필요하고 지금 0.696 ms 이니 12배" 라고 적었다. `sep` 이 **0.051 ms** 다.

절대값으로도 245 ms 대 269 ms 이므로, dkey/akey 로 옮기면 layerwise 가 현재
최선 비layerwise DFS 경로보다 빨라진다. `batch` 까지 쓰면 204 ms 다.

**DPU 논의 이전에 소프트웨어만으로 이만큼이 남아 있다.**

## 뜻밖의 결과: 지금 저장 형태가 가장 불리하다

`one` 팔이 가장 느리다(571 ms, 8.8 GB/s). `batch` 와 dkey 도 바이트도 같고
차이는 40 MiB 를 **단일 extent** 로 두느냐 **1 MiB akey 40 개**로 두느냐뿐인데
2.8배 벌어진다. 서버가 akey 단위로는 병렬로 처리하고 단일 extent 는 한 줄로
처리하는 것으로 보인다.

이는 layerwise 와 무관하게, 청크당 한 객체에 전 레이어를 연속으로 담는 현재
형태가 **그 자체로 손해**일 수 있다는 뜻이다. 별도로 확인할 값어치가 있다.

## 미완: DFS 대조군

위 DFS 수치(0.63 ms)는 TTFT 에서 역산한 것이라 LMCache 엔진 오버헤드가 섞여
있을 수 있다. 순수 저장 계층끼리 비교하려고 같은 프로세스 안에 DFS 팔(`-m dfs`,
평면 네임스페이스에 파일 하나씩)을 넣었으나 **완주하지 못했다.**

- 파일 4 개(t=1, L=2, C=2)에서는 동작하고 **객체당 0.873 ms** 가 나왔다.
- 파일 수를 늘리면 `fi_mr_regattr(... iov_len=1048576 ...) failed, rc: -14
  (Bad address), mr_reg_count=4` 로 실패한다. 등록 수 고갈이 아니다(4 개뿐).
  실패 주소(`0x7efe1effbeb0`)는 **페이지 정렬이 아니어서 우리 버퍼가 아니다** —
  `aligned_alloc(4096, ...)` 로 잡은 뒤 1 MiB 배수 오프셋만 쓴다. dc_array 내부
  버퍼로 보인다. 스레드 수와 무관하고 파일 수에만 반응한다.
- 첫 실패에서 워커가 `exit(1)` 을 부르는 바람에 프로세스가 종료 중 멈춘다.
  이건 하네스 결함이다.

그래서 확정된 것과 아닌 것을 나누면 이렇다.

- **확정**: object API 의 고정 비용은 0.0137 ms 이고, 요구치 0.056 ms 를 넘긴다.
  이 값은 DFS 를 어떻게 재든 변하지 않는다.
- **미확정**: DFS 의 0.63 ms 중 저장 계층 몫이 얼마인가. 단일 스레드 직접 측정이
  0.873 ms 로 나온 것은 대부분이 저장 계층임을 시사하지만, 파일 4 개짜리 표본이다.

배수를 "46배" 로 적지 않고 **"요구치를 넘겼다"** 로만 적는 이유가 이것이다.

## 다음

1. DFS 팔의 등록 실패를 좁힌다. 이것이 DFS 자체의 결함이라면 그 자체로 보고감이다.
2. `one` 대 `batch` 의 2.8배 차이를 확인한다. 지금 형태를 바꿀 근거가 될 수 있다.
3. 위가 정리되면 `DaosConnector` 의 dkey/akey 백엔드를 시제품으로 만든다.
   `daos_obj_fetch_gpu`/`daos_obj_update_gpu` 가 `theodore/b_cufile` 클라이언트에
   있으므로 GPU-direct 경로를 포기하지 않아도 된다(심볼 확인함).

## v3 akey 접기 실측 (2026-09-30, daos-ib 4 rank / verbs)

위 측정이 "객체당 고정 비용"을 지목했으므로, 레이어를 한 dkey 아래 akey 로 접어
**RPC 하나에 iod N개**로 보내도록 커넥터를 연결했다. 그 뒤 raw 컨테이너(PYTHON 레이아웃)에서
접기 대 개별 호출을 직접 쟀다. 40 레이어, 중앙값 5회, 같은 객체 핸들 재사용.

| 레이어 크기 | 쓰기 접기 | 쓰기 개별 | 배속 | 읽기 접기 | 읽기 개별 | 배속 |
|---|---|---|---|---|---|---|
| 4 KiB | 2.85 ms | 7.89 ms | **2.77x** | 2.26 ms | 7.53 ms | **3.33x** |
| 64 KiB | 7.82 ms | 18.20 ms | **2.33x** | 7.08 ms | 15.11 ms | **2.13x** |
| 256 KiB | 53.89 ms | 54.09 ms | 1.00x | 25.21 ms | 31.33 ms | 1.24x |
| 1 MiB | 241.35 ms | 212.87 ms | 0.88x | 240.76 ms | 224.98 ms | 0.93x |
| 4 MiB | 942.72 ms | 862.12 ms | 0.91x | 933.20 ms | 883.27 ms | 0.95x |

**교차점이 256 KiB 부근이다.** 그보다 작으면 RPC 왕복이 지배해 2~3배 이득이고, 크면
대역폭이 지배해 접기가 오히려 5~12% 느리다.

이게 무슨 뜻인지 분명히 해둔다. 레이어 하나의 크기는
`chunk_size(토큰) x KV헤드 x head_dim x 2(K,V) x 2B` 다. Qwen3-14B 는 토큰·레이어당
4096 B 이므로 `chunk_size: 256` 이면 레이어가 1 MiB — **실제로 쓰는 청크 크기에서는
페이로드 접기가 이득이 아니다.**

이득이 남는 곳은 두 군데다.

- **메타데이터**: 40개 헤더가 쓰기 1.3 ms / 읽기 1.9 ms 에 한 RPC 로 끝난다. 개별로 보내면
  작은 RPC 40회(≈7.5 ms)다. 읽기 경로는 헤더를 먼저 읽어야 하므로 이건 항상 붙는 이득이다.
- **작은 청크 구성**: `chunk_size` 를 16~64 토큰으로 낮춘 구성이라면 2배 이상.

### 이 측정의 한계

개별 호출 팔은 **한 스레드에서 순차**로 돌렸다. 실제 커넥터는 16 스레드 풀로 부채꼴
전개하므로, 접지 않은 경로의 실측은 이보다 빠를 수 있다. 즉 위 표의 배속은 접기에
**유리한 쪽으로 기운 비교**이며, 1 MiB 이상에서 접기가 진다는 결론은 그만큼 더 단단하다.
반대로 4~64 KiB 의 2~3배는 상한으로 봐야 한다.

### 왜 거기서 교차하는지 — 이미 규명돼 있다

이 모양은 새로운 발견이 아니라 `doc/RAW-API-PLAN.md` 의 결론을 다른 축에서 재현한
것이다. 그쪽은 **DFS 대 저수준**을 쟀고 여기는 **접기 대 개별**을 쟀는데, 답이 같다.

- RAW-API-PLAN "규명 완료 — 전부 `chunk_size` 다": DFS 가 빠른 이유는 배열 API 가
  바이트 범위를 `chunk_size`(기본 1 MiB) 단위로 **여러 dkey 에 흩고** 한 호출 안에서
  동시에 발행하기 때문이다. 16 MiB 를 dkey 하나에 통째로 넣으면 2.92 GB/s, 1 MiB
  청크로 흩으면 17.80 GB/s — 우리 dkey/akey 배치는 전자에 해당한다.
- 그래서 그 문서의 결론은 **"저수준으로 내려가 얻을 것은 대역폭이 아니라 객체당
  고정비"** 였고, 저수준이 실제로 이긴 곳도 1 MiB 객체의 1.81배(메타데이터·조회 비용)였다.

위 표는 정확히 그것이다. 작은 레이어에서는 고정비가 지배하므로 접기가 2~3배 벌고,
1 MiB 를 넘으면 대역폭이 지배하므로 벌 것이 없다.

**그리고 접기는 이 천장을 못 올린다.** 40 레이어를 한 RPC 로 접어도 그 40개는 여전히
**같은 dkey = 같은 샤드**에 떨어진다. 대역폭을 되찾으려면 배열 API 처럼 dkey 를 흩어야
하는데, 그건 접기와 반대 방향이다. 즉 접기와 스트라이핑은 **양립하지 않는 최적화**이고,
어느 쪽을 택할지는 레이어 크기가 정한다 — 작으면 접기, 크면 흩기.

### 부수적으로 확인한 것

- 정합성: 40/40 메타·페이로드, 내용 일치
- `punch_akeys`(새로 추가): 레이어 7만 지우고 나머지 39개가 남는다. 레이어 하나를 evict 하려고
  dkey 를 punch 하면 나머지 39개가 같이 날아가므로 이 호출이 필요했다.
