# NIXL DAOS 백엔드 실측 (2026-09-12, client-5)

## 요약

400G verbs 위에서 **34.17 GB/s**. 레이어 40개를 한 RPC 로 접었을 때다.
접지 않으면 14.40 GB/s 로 떨어진다.

두 가지가 이 숫자를 만든다. **접기(folding)** 와 **동시성**이다. 그리고 그 둘을
분리해 재는 과정에서 이 문서의 초기 해석 두 개가 틀렸음이 드러났다. 정정을
§4 에 남긴다.

## 1. 환경

client-5, Rocky 10.2 / 커널 6.12, gcc 14.3.1, CUDA 13.3, UCX 1.21.0.
DAOS 2.9.100 stockfull, 랭크 2(cell1/cell2), 타깃 16, 전송 `ofi+verbs;ofi_rxm`,
에이전트 domain `mlx5_0`, ConnectX-7 400G RoCE(PFC 없음).
풀 `attr1`, 컨테이너 `nixlbench`(plain, rd_fac:0).

부하 형태는 `tests/obj_latency.c` 와 같게 맞췄다.
**객체 120 × 레이어 40 × 1 MiB = 4.69 GiB.** 하네스는 `nixl/tests/bench_nixl.cpp`
이며 NIXL 에이전트를 거치지 않고 백엔드를 직접 구동한다.

측정 시점에 client-5 는 유휴였다(GPU 0%, 컨테이너 0개). 다만 `attr1` 풀에는 같은 날
다른 팀이 만든 `discos-gdr-20260912`, `discos-posix-20260912` 가 있다. 동시 I/O 여부는
확인하지 않았다.

## 2. 접기

`prepXfer` 는 같은 (객체, dkey) 를 가진 디스크립터를 모아 `daos_obj_fetch` 한 번으로
만든다. `-f` 로 켜고 끈다.

| | 요청 수 | 읽기 | 대역폭 |
|---|---|---|---|
| `fold=1` (레이어 40개를 요청 1개로) | 120 | **147.3 ms** | **34.17 GB/s** |
| `fold=0` (레이어마다 요청) | 4800 | 349.5 ms | 14.40 GB/s |

둘 다 스레드 64, inflight 64. 바이트는 동일하다. **2.4 배.**

## 3. 동시성

두 변수를 하나씩 고정해 분리했다.

**A. inflight 64 고정, 스레드만 변화 (`fold=0`)**

| 스레드 | 읽기 | 대역폭 |
|---|---|---|
| 16 | 607.8 ms | 8.28 GB/s |
| 32 | 445.8 ms | 11.29 GB/s |
| 64 | 350.8 ms | 14.35 GB/s |
| 128 | 351.9 ms | 14.30 GB/s |

**B. 스레드 64 고정, inflight 만 변화 (`fold=0`)**

| inflight | 읽기 | 대역폭 |
|---|---|---|
| 16 | 630.8 ms | 7.98 GB/s |
| 32 | 453.6 ms | 11.10 GB/s |
| 64 | 349.5 ms | 14.40 GB/s |
| 128 | 348.9 ms | 14.43 GB/s |

**두 표가 같은 곡선이다.** 스레드가 64여도 inflight 가 16이면 8 GB/s 고, 그 반대도
같다. 유효 동시성은 `min(스레드, in-flight 요청 수)` 이며 **64에서 평평해진다.**

그래서 기본 스레드 수를 64로 정했다(`NIXL_DAOS_THREADS` 로 조절). 호출자가 요청을
적게 띄우면 이 값과 무관하게 호출자 쪽 깊이에 묶인다.

`fold=1` 도 스레드에 반응하지만 폭이 작다: 16에서 30.53 GB/s, 64에서 34.17 GB/s.
요청이 120개뿐이라 동시성을 다 쓰지 못한다.

## 4. 정정

측정 도중 내렸던 해석 둘을 철회한다. 둘 다 **동시성이 어긋난 비교**였다.

**(1) "스레드 생성 비용이 병목이다" — 틀렸다.**

요청당 `std::async` 를 스레드풀로 바꾸면 4800 스레드가 16개 재사용으로 바뀐다.
그런데 결과가 624.7 ms → 616.3 ms, **차이 1.3%** 였다. 드라이버가 inflight 16으로
묶고 있었으므로 어느 쪽이든 동시 호출은 16개였다. 생성 비용은 처음부터 병목이
아니었다.

스레드풀은 그대로 유지한다. 이유는 성능이 아니라 구조다. 요청 수만큼 스레드를
만들었다 없애는 것은 측정에 안 잡혀도 메모리·스케줄러 압력이 실재하고, 무엇보다
`NIXL_DAOS_THREADS` 로 **동시성을 조절할 수 있게 된 것이 위 스윕을 가능하게 했다.**

**(2) "NIXL 계층 오버헤드가 없다" — 틀렸다.**

`fold=1` 161.5 ms 가 raw libdaos 의 `batch` 204 ms 보다 빠르다는 데서 나온 결론이었다.
그 raw 측정은 16 스레드가 동기 호출을 순차로 돌린 것이고 이쪽은 파이프라인이라
비교가 성립하지 않는다.

형태와 스레드 수를 맞추면 이렇다.

| 경로 | 4800 요청, 스레드 16 |
|---|---|
| raw libdaos (`tests/obj_latency.c` `sep`) | 245 ms |
| NIXL 백엔드 (`fold=0`) | 607.8 ms |

**요청당 약 0.076 ms** 를 NIXL 경로가 더 쓴다. `prepXfer` 의 `dynamic_cast`,
`std::map` 삽입, 그룹당 벡터 5개 할당, `postXfer` 의 뮤텍스·조건변수가 후보다.

이것이 접기 효과의 정체이기도 하다.

| | 요청 수 | 추정 오버헤드 | 전체 대비 |
|---|---|---|---|
| `fold=1` | 120 | 9 ms | 165 ms 중 5% |
| `fold=0` | 4800 | 363 ms | 608 ms 중 60% |

다만 이 0.076 ms 는 **서로 다른 하네스 간 비교라 통제된 값이 아니다.** 정확히 재려면
같은 드라이버에서 백엔드만 바꿔야 한다. 미측정으로 남긴다.

접기 배수도 정정한다. 동시성이 어긋난 비교에서 3.9배로 봤으나, 맞추면 **2.4배**다.

## 5. 정합성

스레드풀 전환 뒤에도 `nixl/tests/` 두 프로그램이 모두 통과한다. 특히 쓰지 않은 키를
읽을 때 `NIXL_ERR_NOT_FOUND` 가 나오는 것을 확인했다. DAOS 는 그 경우 성공에
`iod_size 0` 으로 답하므로, 그대로 통과시키면 0으로 채워진 버퍼가 적중으로 보고된다.

## 6. 다음

- **요청당 할당·동기화 비용.** 핸들 재사용, 그룹이 하나일 때 `std::map` 우회,
  벡터 사전 예약. §4(2) 의 0.076 ms 를 겨냥한다.
- **통제된 오버헤드 측정.** 같은 드라이버에서 POSIX 백엔드와 DAOS 백엔드를 바꿔
  재면 NIXL 계층 비용이 분리된다.
- **`VRAM_SEG`.** `daos_obj_fetch_gpu` 는 `theodore/b_cufile` 클라이언트에 있다.
  client-5 에는 그 라이브러리가 `/opt/daos-gds-gpu` 에 있으므로 여기서는 가능하다.
- **NIXL 에이전트 경유.** 지금은 백엔드를 직접 구동할 뿐이다.

## 재현

```bash
# client-5, cell1 경유
cd /home/nixl-dev/t
NIXL_DAOS_THREADS=64 ./bench_nixl -p attr1 -c nixlbench \
    -o 120 -l 40 -s 1048576 -i 64 -r 2 -f 1
```

빌드 절차는 `nixl/README.md`. client-5 는 meson·ninja 가 없어 `ensurepip` → pip 로
세웠고, `nvcc` 를 PATH 에 넣어야 하며, DAOS 가 `/var/daos-stockfull` 에 있어 플러그인
`meson.build` 가 프리픽스를 탐색한다.
